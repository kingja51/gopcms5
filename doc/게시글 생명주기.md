`POST /bbs/{siteCode}/{bbsCode}/save` 한 건이 스프링을 통과하는 전 과정.
**브레이크포인트를 어디에 걸고 무엇을 볼지**를 기준으로 썼다. 구현된 것만 적었고,
실측으로 잡은 함정을 각 단계에 붙였다.

## 1. 사전 단계 — `GET /write` 가 PK 를 먼저 발급한다

이 도메인의 저장 로직을 이해하는 열쇠다. 폼을 여는 순간 PK 가 발급된다.

[BoardUsrController.java:142](../src/main/java/com/gonet/primary/board/controller/BoardUsrController.java:142)

```java
article.setArticleId(Uid.next(UidPrefix.BBA));   // 폼을 여는 시점에 발급
```

**왜**: 첨부 picker 가 **저장 전에** 파일을 올린다. 업로드는 `entityId` 를 요구하므로
글 ID 가 그때 이미 있어야 한다. 그래서 `write.html` 의 hidden 에 `articleId` 가 실린다.

**결과**: `save` 로 들어오는 **신규 글도 PK 를 달고 온다.** 이 사실이 5절의 `resolveNew`
설계와 6-3 의 "조용히 사라지는 글" 증상을 모두 설명한다.

> 브레이크포인트: `BoardUsrController:129 write()`.
> `article.getArticleId()` 가 `BBA_` + UUIDv7 형식인지 확인한다.

## 2. 서블릿 필터 체인 — 순서가 계약이다

`@Order` 값이 **작을수록 바깥**이다. 값 자체에 의미가 있으므로 새 필터를 넣을 때
기존 값 사이를 침범하지 말 것.

| Order | 필터 | 하는 일 | 없으면 생기는 증상 |
|---|---|---|---|
| `+5` | [SecurityHeadersFilter:75](../src/main/java/com/gonet/config/web/SecurityHeadersFilter.java:75) | CSP nonce 생성·보안 헤더 | 인라인 스크립트가 CSP 로 전부 차단 |
| `+6` | [AuditorContextFilter:37](../src/main/java/com/gonet/config/web/AuditorContextFilter.java:37) | `AuditorContext.set(null, ip)` | `created_ip`·`updated_ip` 가 NULL |
| `+7` | LoginRateLimitFilter | 로그인 시도 제한 | (이 요청과 무관 — `shouldNotFilter`) |
| `+10` | [AccessLogFilter:66](../src/main/java/com/gonet/config/web/AccessLogFilter.java:66) | 시작시각 기록 → **응답 후** `log_access` 적재 | 접근 로그 공백 |
| `+20` | [SiteResolveFilter:46](../src/main/java/com/gonet/config/web/SiteResolveFilter.java:46) | `SiteContextHolder.set(site)` | 사이트 미해석 → 게시판을 못 찾음 |

### 2.1 `AuditorContextFilter` 는 userId 를 넣지 않는다

```java
AuditorContext.set(null, clientIpResolver.resolve(request));   // userId = null
```

일부러 null 이다. 이 필터는 시큐리티 **바깥**이라 아직 인증 주체를 모른다.
`AuditorContext.currentUserId()` 는 홀더가 비어 있으면
[authenticatedUserId()](../src/main/java/com/gonet/common/audit/AuditorContext.java:47) 로
`SecurityContextHolder` 를 직접 본다 — **그래서 감사컬럼이 채워진다.**

> 브레이크포인트: `AuditorContext:33 currentUserId()`.
> `HOLDER.get().userId == null` 이고 반환값은 `MBR_…` 이어야 정상이다.
> 둘 다 null 이면 인증이 안 된 상태로 저장 지점까지 온 것이다.

### 2.2 사이트는 **두 번째** 세그먼트에서 온다

게시판은 `PROGRAM` 네임스페이스다([UrlNamespaces](../src/main/java/com/gonet/common/web/UrlNamespaces.java) — `PROGRAM = {"bbs", "prg"}`).

```
/{siteCode}/{slug}          컨텐츠 → 첫 번째 세그먼트
/bbs/{siteCode}/{bbsCode}   프로그램 → 두 번째 세그먼트
/adm/**                     SKIP → 사이트 개념 없음
```

해석 순서는 ① 경로의 사이트코드 자리 → ② `?siteCode=` → ③ 기본 사이트.
**③ 때문에 실패해도 null 이 되지 않는다** — 오타 난 siteCode 는 기본 사이트로 조용히
빠지고, 그 사이트에 없는 `bbsCode` 라서 "게시판을 찾을 수 없습니다" 로 나타난다.

> 브레이크포인트: `SiteResolveFilter:46`.
> `SiteContextHolder.get().getSiteCode()` 가 URL 의 siteCode 와 같은지 확인한다.
> 다르면 ③ 폴백이 작동한 것이고, 원인은 URL 오타이거나 사이트 `use_yn='N'` 이다.

## 3. Security FilterChain — 컨트롤러 앞의 두 관문

`/bbs/**` 는 `@Order(1)` 의 `securityMatcher("/adm/**")` 에 걸리지 않으므로
[defaultSecurityFilterChain](../src/main/java/com/gonet/config/security/SecurityConfig.java:90)
(`@Order(2)`)이 담당한다.

### 3.1 CSRF — 실패하면 컨트롤러에 도달하지 못한다

`write.html` 의 `<form method="post">` 에는 Thymeleaf 가 `_csrf` hidden 을 자동 삽입한다.
`th:action` 을 쓰기 때문에 작동한다 — **순수 `action=` 으로 바꾸면 토큰이 사라진다.**

예외는 NICE 콜백 2경로뿐이고 게시판은 포함되지 않는다.

> 증상: 저장 버튼을 눌렀는데 **403** 이고 컨트롤러 로그가 전혀 없다.
> 확인: `CsrfFilter#doFilterInternal`, 또는 브라우저 개발자도구에서 요청 payload 에
> `_csrf` 가 실렸는지. htmx 로 보낼 때는 헤더/파라미터 누락이 흔하다.

### 3.2 인가 — DB 단일 원천, 무매칭 DENY

[DynamicAuthorizationManager:52](../src/main/java/com/gonet/config/security/DynamicAuthorizationManager.java:52)

`/bbs/**` 는 `PERMIT_ALL`(priority 200)이다 —
[V912__seed_url_access_program.sql](../src/main/resources/db/devdata/primary/V912__seed_url_access_program.sql)

```sql
('…1981', NULL, NULL, '/bbs/**', 'ALL', 'PERMIT_ALL', NULL, NULL, 200,
 '게시판 사용자 화면 — 읽기/쓰기 권한은 tb_bbs_master 가 판정'),
```

**URL 인가는 여기서 끝난다.** 게시판별 읽기·쓰기 권한은 URL 로 표현할 수 없어
(게시판마다 다르다) 서비스 계층이 `tb_bbs_master.read_auth`/`write_auth` 로 판정한다.
**두 층을 혼동하지 말 것** — URL 이 열려 있다고 글을 쓸 수 있는 것이 아니다.

> 증상: 로그에 `접근 규칙 없음 → DENY: POST /bbs/…` WARN.
> 원인은 규칙 미등록이며, 해법은 SecurityConfig 수정이 아니라 규칙 INSERT
> (절차: [conventions.md §7](conventions.md)). 규칙을 DB 에서 직접 고쳤다면
> `/adm/url-access` 의 "캐시 비우기" 를 눌러야 반영된다.

## 5. 서비스 — 정책이 실행되는 곳

[BoardArticleServiceImpl:62 save()](../src/main/java/com/gonet/primary/board/service/BoardArticleServiceImpl.java:62)

### 5.0 트랜잭션 경계

클래스에 `@Transactional(readOnly = true, transactionManager = PRIMARY_TX)` 가 걸려 있고
`save()`·`delete()`·`increaseViewCount()` 가 **쓰기용으로 override** 한다.

```java
@Override
@Transactional(transactionManager = MyBatisConfig.PRIMARY_TX)   // readOnly 해제
public void save(...)
```

> **override 를 빠뜨리면** 클래스 레벨 `readOnly=true` 가 상속돼 INSERT 가
> `Connection is read-only` 로 실패한다. CLAUDE.md 가 경고하는 함정이다.
> 브레이크포인트: `TransactionAspectSupport#invokeWithinTransaction`,
> 또는 간단히 `TransactionSynchronizationManager.isCurrentTransactionReadOnly()`.

컨트롤러의 `try/catch (IllegalArgumentException)` 는 **트랜잭션 밖**이다
([BoardUsrController:167](../src/main/java/com/gonet/primary/board/controller/BoardUsrController.java:167)) —
서비스가 던지면 롤백이 먼저 끝나고 컨트롤러가 flash 메시지로 되돌린다.

### 5.1 합본(aggregator) 차단 — UI 가드로는 부족하다

```java
if (master.isAggregator()) {
    throw new AccessDeniedException("통합 게시판에는 글을 쓸 수 없습니다…");
}
```

화면에서 버튼만 감추면 URL 직접 호출로 뚫린다. 원전이 UI 가드만 두고 서비스 가드를
미뤄 실제로 열려 있던 구멍이다.

### 5.2 쓰기 권한 — `write_auth` 실행

[requireWritePermission:230](../src/main/java/com/gonet/primary/board/service/BoardArticleServiceImpl.java:230)

| `write_auth` | 판정 |
|---|---|
| `MEMBER` | 로그인만 되어 있으면 통과 |
| `ADMIN` | `ROLE_STAFF` 이상 (역할 계층상 STAFF·MANAGER·ADMIN 포함) |

비로그인은 `InsufficientAuthenticationException`(→ 로그인 유도),
권한 부족은 `AccessDeniedException`(→ 403). **둘을 구분하는 것이 의도**다 —
"로그인하면 열릴 수도 있는 상태" 와 "영구 거부" 는 다른 응답이어야 한다.

역할 계층은 [SecurityConfig:56](../src/main/java/com/gonet/config/security/SecurityConfig.java:56):

```
ROLE_ADMIN > ROLE_MANAGER > ROLE_STAFF > ROLE_MEMBER > ROLE_REAL
```

### 5.3 검증

[validate:258](../src/main/java/com/gonet/primary/board/service/BoardArticleServiceImpl.java:258) —
제목·내용 필수, **공지 지정은 `ROLE_STAFF` 이상**, 영상 게시판은 `link_url` 필수.

공지에 권한을 두는 이유: 공지는 목록 맨 위를 차지하고 **첨부까지 공개로 바뀐다**(5-6).

### 5.4 정규화 — 클라이언트 값을 덮어쓰는 지점

[normalize:275](../src/main/java/com/gonet/primary/board/service/BoardArticleServiceImpl.java:275)

```java
a.setWriterUserId(writer.userId());       // 폼 hidden 을 믿지 않는다
a.setWriterUserType(writer.userType());
a.setClientIp(AuditorContext.currentIp());
if ("Y".equals(master.getHtmlYn())) {
    a.setContent(HtmlSanitizer.sanitize(a.getContent()));
}
```

- **작성자는 세션에서 온다.** 폼 hidden 을 믿으면 남의 이름으로 글이 올라간다
- **본문 정화는 저장 시점 한 번.** 렌더에서 하면 화면마다 빠뜨릴 수 있고 DB 에는
  위험한 마크업이 그대로 남는다. `html_yn='N'` 인 평문 게시판은 손대지 않는다
  (렌더에서 이스케이프)

> 브레이크포인트: `HtmlSanitizer:53 sanitize()`.
> 정화 **전/후** 문자열을 비교한다. 에디터 서식이 사라진다는 신고는 대개 이 allowlist
> 문제이고, allowlist 는 Tiptap·CrossEditor 두 에디터 출력의 **합집합**으로 잡혀 있다.

### 5.5 신규/수정 판정 — **PK 유무로 판정하면 안 된다**

[resolveNew:132](../src/main/java/com/gonet/primary/board/service/BoardArticleServiceImpl.java:132)

1절에서 본 대로 신규 글도 PK 를 달고 온다. 그래서 **DB 에 실제로 있는지 물어서** 정한다.

```java
BbsArticleAdmDto existing = bbsArticleMapper.findById(id);
if (existing == null) { return true; }        // 신규
```

같은 메서드가 세 가지를 더 막는다:

| 검사 | 막는 것 |
|---|---|
| `id.matches(Uid.PATTERN)` + `BBA_` 접두어 | 형식이 틀린 PK 주입 |
| `master.bbsMasterId != existing.bbsMasterId` | 다른 게시판의 글을 이 URL 로 수정 |
| `!canManage(existing)` | 남의 글 수정 (쓰기 권한 ≠ 수정 권한) |

> **실측 결함**: PK 유무로 판정하던 시절, 신규 글이 "수정" 으로 오인돼 존재하지 않는
> 행을 UPDATE → **0건 갱신으로 조용히 사라졌다.** 예외도 로그도 없이 302 리다이렉트만
> 정상으로 보이는 최악의 증상이다.
> 브레이크포인트: `resolveNew` 반환값과 `bbsArticleMapper.update()` 의 반환 rowcount.

### 5.6 첨부 다운로드 권한 — 공지는 마스터 정책을 이긴다

[resolveArticleDownloadAuth:248](../src/main/java/com/gonet/primary/board/service/BoardArticleServiceImpl.java:248)

```java
if (article.isNotice()) { return DownloadAuth.ANONYMOUS; }   // 강제
```

공지는 알리려고 올리는 글이라 첨부(공고문·서식)가 로그인 뒤에 숨으면 목적을 잃는다.

### 5.7 첨부 동기화

[syncAttachments:307](../src/main/java/com/gonet/primary/board/service/BoardArticleServiceImpl.java:307)

`attachments` CSV 에 남은 파일 ID 만 유지하고 나머지는 soft delete.
그룹은 **폼 저장 시점에 정책과 함께** 만든다 — picker 가 먼저 만들게 두면
DB 기본값(`ROLE_MEMBER`)이 박힌 그룹이 잠깐 존재하는 창이 생긴다.

```java
String groupId = fileService.ensureGroup(ENTITY_TYPE /* "BBS" */, a.getArticleId(),
                                         master.getSiteId(), downloadAuth);
fileService.syncAttachments(groupId, keep);
a.setFileGroupId(keep.isEmpty() ? null : groupId);   // 첨부 0건이면 참조를 끊는다
```

첨부가 전혀 없고 그룹도 없으면 아무 것도 하지 않고 빠져나간다(불필요한 그룹 생성 방지).

## 6. MyBatis — 감사컬럼과 SQL

### 6.1 AuditInterceptor 가 먼저 끼어든다

[AuditInterceptor:28](../src/main/java/com/gonet/common/audit/AuditInterceptor.java:28) —
`Executor#update` 를 감싸는 플러그인이며 3개 SqlSessionFactory 에 공통 등록된다.

`BbsArticleAdmDto extends Auditable` 이므로 대상이다. INSERT 면 6종, UPDATE 면 3종을
채우고 **이미 값이 있으면 덮어쓰지 않는다**(마이그레이션·배치의 명시 값 존중).

```
created_by / created_ip / created_at + updated_by / updated_ip / updated_at
```

> 브레이크포인트: `AuditInterceptor:28`.
> `AuditorContext.currentUserId()` 가 `MBR_…` 인지 확인한다. null 이면 감사컬럼이
> 비어 저장되고, 원인은 2-1 의 SecurityContext 이거나 **요청 밖 스레드**다.

### 6.2 INSERT

[BbsArticleMapper_maria.xml:87](../src/main/java/com/gonet/primary/board/mapper/BbsArticleMapper_maria.xml:87) —
전량 `#{}` 바인딩(`${}` 금지). `created_at`·`updated_at` 은 DB 의 `CURRENT_TIMESTAMP` 를 쓴다.

## 7. 응답 — 리다이렉트와 필터 되감기

### 7.1 PRG 패턴

```java
return "redirect:" + base(siteCode, bbsCode) + "/" + article.getArticleId();
```

`302` + `Location: /bbs/ai/notice/BBA_…`. 저장 실패(`IllegalArgumentException`)면
`/write?articleId=…` 로 되돌리며 flash 로 메시지를 넘긴다 — **PK 를 함께 넘기므로
이미 올린 첨부가 유지된다.**

### 7.2 되감기 순서 — `finally` 블록들

바깥 필터가 나중에 끝난다. 이 순서에 의존하는 코드가 둘 있다:

- **ActorCaptureFilter** 는 `finally` 에서 `request.setAttribute(ACTOR, principal)` 한다.
  체인 안쪽에 있어야 하고, **빈으로 등록해서는 안 된다** — Boot 가 Filter 빈을 서블릿
  체인 최외곽에도 자동 등록하는데 `OncePerRequestFilter` 는 한 번만 돌므로 바깥
  인스턴스가 선점하면 SecurityContext 가 비워진 뒤 실행돼 actor 가 항상 null 이 된다.
  그래서 `SecurityConfig` 가 `new` 로 직접 만든다.
- **AccessLogFilter** 는 그 attribute 를 읽어 `log_access` 를 적재한다. 시큐리티 체인이
  이미 반환된 시점이라 `SecurityContextHolder` 는 비어 있다.

적재 실패는 삼키고 `log_error` 로 올린다(60초 스로틀) —
[member-domain.md §2.7](member-domain.md#27-삼킨-실패는-log_error-로-끌어올린다).

### 7.3 리다이렉트 후 GET — 뷰 해석 3단 폴백

컨트롤러는 논리 뷰명 `front/board/detail` 만 반환한다.
[SiteTemplateViewResolver:41](../src/main/java/com/gonet/config/view/SiteTemplateViewResolver.java:41)
가 물리 경로로 재작성한다:

```
front/board/detail
  → sites/{siteCode}/board/detail      ① 사이트 전용 (있으면)
  → layouts/{layoutCode}/board/detail  ② 레이아웃 오버라이드
  → layouts/_default/board/detail      ③ 공용 1벌
```

현재 `layouts/_default/board/detail.html` 만 존재하므로 ③으로 떨어진다.

> **뷰 캐시가 켜져 있으면** 템플릿을 고쳐도 반영되지 않는다. 재기동 필요.
> `DevTools 는 금지`(CLAUDE.md — Virtual Threads + HikariCP + Windows JVM 크래시 이력).

## 10. 컨텍스트 수명 — ThreadLocal 4종

저장 로직이 의존하는 요청 스코프 값들. **범위를 벗어나면 전부 null 이 된다.**

| 홀더 | 세우는 곳 | 지우는 곳 | 쓰는 곳 |
|---|---|---|---|
| `SiteContextHolder` | SiteResolveFilter(+20) | 같은 필터 `finally` | `requireMaster`, ViewResolver |
| `AuditorContext` | AuditorContextFilter(+6) | 같은 필터 `finally` | `normalize`, AuditInterceptor |
| `SecurityContextHolder` | SecurityContextHolderFilter | 시큐리티 체인 종료 | 권한 판정, `authenticatedUserId()` |
| MDC `traceId` | micrometer-tracing-bridge-brave | 요청 종료 | `sql.log`, `log_access`, `log_error` |

> **`@Async`·배치·스케줄러에서는 넷 다 비어 있다.** 게시글 저장을 비동기로 옮기면
> 작성자·IP·감사컬럼이 통째로 null 이 된다. 값을 파라미터로 넘겨야 한다.
> `SiteContextHolder` 는 `ThreadLocal` 이라 **Virtual Thread 사이에서도 전파되지 않는다** —
> `AccessLogFilter` 가 `SiteContextHolder` 대신 request attribute 를 읽는 이유가 이것이다
> (내부 필터의 `finally` 가 이미 지운 뒤에 실행된다).

## 11. 관리자 경로와의 차이

[BoardArticleAdmController:86](../src/main/java/com/gonet/primary/board/controller/BoardArticleAdmController.java:86)
(`POST /adm/board/{bbsMasterId}/article/save`)는 **같은 서비스 메서드를 부른다.**
달라지는 것은 앞단뿐이다:

| | 사용자 `/bbs/{siteCode}/{bbsCode}/save` | 관리자 `/adm/board/{bbsMasterId}/article/save` |
|---|---|---|
| Security 체인 | `@Order(2)` default | `@Order(1)` `/adm/**` + 2FA 필터 |
| 인가 규칙 | `/bbs/**` PERMIT_ALL (pri 200) | `/adm/**` ROLE_ADMIN (pri 20) |
| 사이트 해석 | SiteResolveFilter 적용 | **SKIP** — `UrlNamespaces.SKIP` 에 `adm` 이 있다 |
| 게시판 식별 | `bbsCode` + 현재 사이트 | `bbsMasterId`(PK) 직접 |
| 뷰 해석 | Resolver 3단 폴백 | 재작성 제외(`adm/**` 직접) |
| 서비스 | `BoardArticleService#save` | **같은 메서드** |

정책을 서비스에 둔 결과다. 두 경로에 각각 판정을 두면 한쪽만 고쳐져 갈린다 —
그래서 `resolveNew` 의 "다른 게시판 글 수정 차단" 같은 검사가 두 경로에 동시에 적용된다.
